## All verified findings by subsystem

### Server: auth & sessions (`server-auth`) — 10 findings
> The auth subsystem is, on the whole, well-engineered and security-aware: HS256 is pinned on both sign and verify (plugins/auth.ts:42-43) to block algorithm-confusion; token_version revocation is wired into logout, password change, role change, and deactivation; refresh tokens are rotated and bound to expiry; login has timing-safe dummy-bcrypt to resist username enumeration; the JWT secret is entropy-validated at boot (config.ts:95-116); and WS auth uses single-use, 60s-TTL tickets instead of tokens-in-query. The weak spots are: (1) WebSocket connections perform NO token_version recheck after the handshake, so a revoked/deactivated/role-changed user keeps a live, fully-privileged socket indefinitely — the single most impactful gap; (2) no self-lockout / last-admin guard, so an admin can deactivate or demote themselves or the only admin and brick all admin access; (3) rate limiting is keyed purely on IP, so per-account brute force from rotating IPs is uncapped and authenticated abuse (password change) isn't keyed per user; (4) several response-shape inconsistencies between login and refresh; and (5) refresh-token reuse-detection is absent (rotation deletes the old token but a replayed stolen token just 401s without revoking the family). None are catastrophic given the loopback-default deployment, but the WS-revocation gap and last-admin guard should be fixed.

- **[high/security/M] WebSocket sessions are never re-validated against token_version after handshake** — `server/src/ws/handler.ts:77-92; server/src/plugins/auth.ts:20-34`
  - issue: WS auth validates a single-use ticket at connect time (handler.ts:77) and stores userId/username on the client. The ticket carries no token_version, and after the connection is established there is no periodic recheck of getTokenVersion(). Consequently, when a user logs out, changes password, is deactivated, has their role changed, or is deleted (all of which bump token_version and/or set active=0), any WebSocket they already hold stays open and fully functional — terminal, Claude sessions, file events, locks — until they voluntarily disconnect. JWT revocation is therefore effectively bypassed for the long-lived channel that matters most. A WS connection can also outlive the 24h JWT TTL entirely since nothing re-checks expiry.
  - fix: Embed token_version in the ws-ticket (issueWsTicket should capture user.token_version) and store it on AuthenticatedSocket; then on each inbound privileged message — or on a periodic timer (e.g. every 30-60s in the existing connectedClients loop) — call getTokenVersion(client.userId) and socket.close(4003, 'Session revoked') when it returns null or mismatches. On logout/deactivation/role-change/password-change, also proactively iterate connectedClients and close sockets for that userId.
- **[high/bug/S] No last-admin / self-lockout guard on user deactivation, deletion, or role demotion** — `server/src/routes/auth.ts:287-341 (PATCH/DELETE /auth/users/:id); db/database.ts:156-161`
  - issue: PATCH /auth/users/:id lets an admin set their own role to 'user' or active:false, and DELETE deactivates any user including the caller or the sole remaining admin. There is no check for 'is this the last active admin?' and no 'cannot modify your own active/role' guard. If the only admin deactivates or demotes themselves (or deletes the last admin account), every admin-only route (including user management itself) becomes permanently unreachable through the API — the system is bricked with no in-app recovery path. token_version is bumped and refresh tokens wiped (auth.ts:317-320), so even existing sessions are killed immediately.
  - fix: Before applying a demotion/deactivation/deletion, count active admins (SELECT COUNT(*) FROM users WHERE role='admin' AND active=1) and reject (409) if the operation would drop it to zero. Additionally reject self-deactivation/self-demotion/self-deletion (request.user.userId === id) with a clear error so an admin can't accidentally lock themselves out.
- **[medium/security/M] No refresh-token reuse detection; rotation alone doesn't revoke a stolen token family** — `server/src/routes/auth.ts:118-148`
  - issue: Refresh tokens are rotated (old deleted, new inserted) which is good, but there is no reuse/replay detection. If an attacker exfiltrates a refresh token and uses it before the legitimate user, the attacker gets the rotated token and the user's next refresh simply fails with 401 'Invalid or expired refresh token' (line 123) — silently, with no audit entry and no revocation of the attacker's now-active session. A presented-but-unknown refresh token is the canonical signal of theft, yet here it's treated as a benign expiry. There is also no audit() call anywhere in the refresh path, so refresh activity is invisible in the audit log.
  - fix: On presentation of a syntactically-valid but unknown/already-rotated refresh token belonging to a known user, treat it as compromise: bumpTokenVersion(user) + DELETE all refresh_tokens for that user (kill the whole family) and audit('refresh_reuse_detected'). To distinguish 'rotated' from 'never existed', store a family/session id or keep a short-lived tombstone of recently-rotated tokens. At minimum, add audit() entries for successful and failed refresh.
- **[medium/security/M] Rate limiting is IP-keyed only — no per-account lockout; password-change limit also IP-keyed** — `server/src/app.ts:52-62 (keyGenerator); server/src/routes/auth.ts:41-47, 196`
  - issue: Login/refresh/password limits (5 / 5min) are keyed solely on CF-Connecting-IP or socket IP. An attacker rotating IPs (trivial behind botnets, or even just multiple Cloudflare egress IPs) can brute-force a single account with no per-username throttle, since nothing keys on or locks the targeted account. Symmetrically, the PATCH /auth/password limit (authRateLimit, line 196) is keyed on IP, not user, so it neither protects a specific account nor meaningfully constrains an authenticated attacker who already holds a valid JWT. There is also no account lockout / progressive backoff after repeated failures.
  - fix: Add a per-username failure counter (in the DB or an in-memory map) that throttles or temporarily locks an account after N consecutive failed logins, independent of source IP. For authenticated routes like password change, key the limiter on request.user.userId instead of IP. Consider auditing repeated login_failed bursts.
- **[low/quality/S] Response shape inconsistency between /auth/login and /auth/refresh** — `server/src/routes/auth.ts:93 vs 147`
  - issue: /auth/login returns data: { token, refreshToken, expiresIn, user }, but /auth/refresh returns data: { token, refreshToken } — no expiresIn and no user. Clients that read expiresIn to schedule proactive refresh (or read user to keep role in sync) get undefined after a refresh, so a role change picked up on refresh isn't reflected client-side, and refresh scheduling silently breaks. expiresIn is also the raw config string '24h' rather than seconds, which is ambiguous for clients expecting a number.
  - fix: Make /auth/refresh return the same envelope as login (include expiresIn and the current user object with up-to-date role). Standardize expiresIn to a numeric seconds value derived from config.jwt.expiresIn so clients don't have to parse '24h'.
- **[low/reliability/S] refresh-token expiry parsing duplicated and silently defaults to 7d on malformed config** — `server/src/routes/auth.ts:87, 136, 344-355; config.ts:47`
  - issue: parseDuration() lives in auth.ts (duplicating the duration math that @fastify/jwt already does for JWT expiry) and, on any string not matching /^(\d+)(s|m|h|d)$/, silently returns 7 days (line 346). A typo in REFRESH_TOKEN_EXPIRES_IN (e.g. '7days', '1w', '604800') yields a 7-day refresh window with no warning, diverging from operator intent. The value is never validated at config load (config.ts only validates the JWT secret and workspace root).
  - fix: Validate refreshExpiresIn (and ideally expiresIn) format at startup in config.ts and fail-fast or warn on malformed values, rather than silently defaulting deep inside the route. Centralize parseDuration in a shared util to avoid drift.
- **[low/quality/S] Admin can create accounts and change passwords with no upper-bound abuse logging; user_created/password_changed not rate-isolated from login** — `server/src/routes/auth.ts:17-19, 196, 253`
  - issue: authRateLimit reuses the same loginMax/loginWindow (5/5min) for POST /auth/users and PATCH /auth/password. Because @fastify/rate-limit buckets per route, this is functionally separate from login, but the semantics are conflated: a legitimate admin onboarding several users in a burst can hit the same tiny 5-request limit meant for credential-guessing, returning 429 to a trusted admin operation. The limit value was chosen for anti-bruteforce, not for admin throughput.
  - fix: Use a separate, looser rate-limit config for admin write operations (or key it on userId), distinct from the anti-bruteforce login window, so admin bulk operations aren't throttled by a value tuned for attackers.
- **[low/reliability/S] GET /auth/users and DELETE /auth/users/:id have no rate limit; ws-ticket issuance unbounded** — `server/src/routes/auth.ts:236-248, 327-341, 164-170; app.ts:51 (global:false)`
  - issue: Rate limiting is global:false, so only routes with an explicit config.rateLimit are limited. GET /auth/users, DELETE /auth/users/:id, GET /auth/me, and POST /auth/ws-ticket carry no limiter. A holder of a valid JWT can call /auth/ws-ticket or /auth/me in a tight loop unthrottled; while these require auth, the absence of any ceiling means a single compromised token can drive unbounded ticket generation (each insert into an in-memory map) or DB load.
  - fix: Add a modest authenticated rate limit (keyed on userId) to ws-ticket issuance and the listing/me endpoints, or enable a sane global default and opt specific routes out, so no authenticated endpoint is entirely unbounded.
- **[low/quality/S] PATCH /auth/users/:id allows no-op fields and returns an oddly-shaped response with undefined active** — `server/src/routes/auth.ts:307-323`
  - issue: The response is `{ id, ...fields, active: fields.active !== undefined ? !!fields.active : undefined }`. When only role is updated, the spread already omits active, but the explicit `active: undefined` is then serialized away by JSON, so the client gets `{ id, role }` — fine — but when active IS updated, `...fields` spreads `active: 1|0` (the DB-shaped int) and the trailing key overwrites it with a boolean, relying on key-order overwrite which is fragile and non-obvious. The endpoint also cannot update username (not in the schema) even though updateUser supports it, and there's no uniqueness re-check path. Minor, but the response normalization is error-prone.
  - fix: Build the response object explicitly from normalized values rather than spreading raw DB-shaped fields and patching one key afterward. Return the canonical user view (same shape as GET /auth/me) so clients have a single contract.
- **[low/security/S] DUMMY_HASH bcrypt cost can diverge from real hash cost, partially undermining timing-equalization** — `server/src/routes/auth.ts:14, 64, 69, 225, 279`
  - issue: DUMMY_HASH is hardcoded at cost 12 (line 14) and real hashes are created at cost 12 (lines 225, 279), so today they match. But the cost is duplicated as a literal in three places with no shared constant; if an operator later raises the real bcrypt cost (or imports users hashed at a different cost), the unknown-user compare against the cost-12 DUMMY_HASH will be measurably faster than a real compare, re-opening the username-enumeration timing channel the dummy hash exists to close.
  - fix: Define a single BCRYPT_COST constant and use it for DUMMY_HASH and every bcrypt.hash call so the timing-equalization invariant can't silently drift.

### Server: files routes, filesystem service, path-guard (`server-files`) — 16 findings
> The subsystem is reasonably well-built and noticeably hardened: path-guard.ts blocks drive letters, UNC paths, NUL bytes, multi-level `..`, protected segments (.git/.ssh/.env/etc.), and now symlink escapes via realpath; unzipToDirectory has zip-bomb defenses (entry count, per-file and total size caps, plus traversal rejection); errors are sanitized in the global handler; secrets are hidden from listings. However there are real correctness and operational gaps. The biggest functional bug is lock-key inconsistency: lock endpoints store/check the raw client path string while listing/info annotate using the normalized relative path, so locks silently fail to match across path aliases (leading slash, trailing slash, `./`, `..` segments) — undermining the entire collaborative-lock feature and the lock checks guarding update/delete. The whole subsystem also buffers every file fully into memory (read, serve, download, zip, upload, unzip) with imported-but-unused streaming primitives, so large files and directory zips will spike memory and can OOM the server despite the 50MB read cap not applying to serve/download/zip. Several write operations (rename/move/copy) silently clobber existing targets, create/upload/rename lack lock checks, and the symlink guard adds a synchronous realpath+existsSync walk on the hot path of every fs call.

- **[high/bug/M] Locks keyed by raw client path; never normalized, so lock matching is unreliable** — `server/src/routes/files.ts:21,100,114,157,230,243,255,262; server/src/services/lock.service.ts:14-118`
  - issue: Lock endpoints (acquire/release/refresh/isLocked/getLock) store and query the verbatim client-supplied `path` string with no canonicalization. But listDirectory (line 21) and getFileInfo (line 157) annotate lock state using `entry.path`/`info.path`, which are produced by relativePath() — always relative with no leading slash (e.g. `src/app.ts`). A client that locks `/src/app.ts` (leading slash) stores key `/src/app.ts`, but the listing annotates with key `src/app.ts`, so getLock returns null and the file shows as unlocked. Worse, isLocked() in PUT /update (line 100) and DELETE /delete (line 114) is similarly aliasable: `src/app.ts`, `/src/app.ts`, `./src/app.ts`, `src/app.ts/`, and `src/foo/../app.ts` all resolve to the same file but produce distinct lock keys, so the lock guard can be trivially bypassed by varying the path spelling. The lock feature's core promise (prevent concurrent edits) is therefore not enforced.
  - fix: Canonicalize the path to a single form before any lock read/write. Compute `relativePath(safePath(path))` once per request and use that string as the lock key everywhere (acquire, release, refresh, isLocked, getLock, getLocksForProject) and for annotation. Centralize this in the route layer or push safePath/relativePath into lock.service.
- **[high/bug/M] create/upload/rename/move/copy bypass lock checks entirely** — `server/src/routes/files.ts:79-90,124-151,175-205`
  - issue: Only PUT /update (line 100) and DELETE /delete (line 114) consult lockService.isLocked. POST /create, POST /rename, POST /move, POST /copy, and POST /upload perform no lock check. A user can rename, move, overwrite (upload to same path), or delete-by-replace a file another user holds a lock on, defeating the lock mechanism. rename/move/upload can also destroy the locked file's path out from under the lock holder.
  - fix: Add isLocked checks to rename, move, copy (dest), and upload (when overwriting an existing path). For rename/move, also relocate or invalidate any lock on the old path so it doesn't dangle.
- **[high/perf/L] serve/download/zip read entire files and directories into memory — OOM risk, 50MB cap not applied** — `server/src/routes/files.ts:55,72,212; server/src/services/filesystem.ts:71-74,142-153,161-210`
  - issue: readFileBinary (line 71-74) does an unbounded readFile with no size cap (the 50MB guard only exists in readFileContent, not the binary path used by /serve and /download). zipDirectory (142-153) accumulates the whole archive into a chunks[] array via Buffer.concat, and unzipToDirectory calls file.buffer() per entry. /upload also buffers the full body into chunks then Buffer.concat (files.ts:183-187). With the 100MB multipart limit and 100MB per-zip-entry limit, a few concurrent serve/download/zip/upload requests can exhaust heap and crash the process. The streaming primitives createReadStream/createWriteStream/pipeline are imported (filesystem.ts:4,6) but never used.
  - fix: Stream responses: for /serve and /download of a file, use reply.send(createReadStream(absPath)) with Content-Length from stat. For directory download, pipe archiver directly into reply (archive.pipe(reply.raw)) instead of buffering. For unzip, stream each entry to disk with pipeline(file.stream(), createWriteStream(...)) while counting bytes. Apply an explicit size cap (or stream) in readFileBinary.
- **[medium/bug/S] rename/move silently overwrite an existing destination file** — `server/src/services/filesystem.ts:109-122`
  - issue: renameEntry (line 113) and moveEntry (line 121) call fs.rename, which on POSIX silently overwrites an existing destination file with no error. renameEntry computes `join(dirname(absOld), newName)` and moveEntry computes `join(absDest, basename(absSrc))` with no existence check, so a rename/move onto an existing file destroys it irrecoverably and the API returns success. createFile correctly guards against overwrite (lines 86-91); these do not.
  - fix: Before rename, stat the target with access() and throw a 409-style error if it exists (unless an explicit overwrite flag is passed). Same for moveEntry's computed target.
- **[medium/bug/S] copyEntry destination semantics ambiguous and can clobber; no existence guard** — `server/src/services/filesystem.ts:124-128; server/src/routes/files.ts:144-151`
  - issue: copyEntry resolves destPath via safePath and calls fs.cp(absSrc, absDest, {recursive:true}) with no `force`/`errorOnExist` and no existence check. fs.cp defaults to force:true, so copying onto an existing file overwrites it silently. The route contract (`destPath`) is also ambiguous: unlike move (which takes a dest *directory* and appends basename), copy takes a full dest path, so callers can accidentally overwrite arbitrary files. Combined with no lock check, a copy can silently destroy a locked file.
  - fix: Pass {recursive:true, errorOnExist:true, force:false} to fs.cp (or pre-check with access) and surface a clear conflict error; document/normalize whether destPath is a directory or a full path consistently with move.
- **[medium/perf/M] Synchronous realpathSync + existsSync walk runs on every fs operation (hot path)** — `server/src/utils/path-guard.ts:88,93-116`
  - issue: safePath() calls assertNoSymlinkEscape on every invocation, which does realpathSync(workspaceRoot) plus a loop of synchronous existsSync()/dirname() calls up the tree and a final realpathSync. These are blocking syscalls on Node's main thread. safePath is invoked for every list entry indirectly (listDirectory stats each entry but safePath only on the dir — OK), but it runs per request for read/serve/download/info, and the symlink walk's existsSync loop adds multiple stat syscalls per call. Under bursty listing/search of deep trees this serializes blocking I/O on the event loop.
  - fix: Cache realpathSync(workspaceRoot) once at startup (it never changes). Consider gating the per-call symlink walk behind a config flag, or only running it for write/delete/move operations rather than every read, since the string-based traversal checks already block literal escapes. If retained, prefer an async variant off the hot path.
- **[medium/security/L] Symlink guard only checks the deepest existing component, missing intermediate symlinked dirs in some operations** — `server/src/utils/path-guard.ts:93-116`
  - issue: assertNoSymlinkEscape walks up to the deepest *existing* path component and realpaths only that. This correctly catches a symlinked leaf or symlinked parent for read/single-file cases. However it does not defend against an intermediate symlink that is created/replaced between the check and the fs operation (TOCTOU): safePath validates, then writeFileContent/copyEntry/rename act on the literal `absolute` path, allowing a race where a symlink swapped in after validation redirects the write outside the workspace. Also, operations like fs.cp/rm with recursive traversal can follow symlinks *inside* a copied/deleted tree that were never passed through safePath at all.
  - fix: For write/delete/move/copy, operate on file descriptors opened with O_NOFOLLOW where possible, or re-validate via realpath immediately before the syscall. For recursive rm/cp, pass options to not dereference symlinks (rm already won't follow; for cp consider verbatimSymlinks or dereference:false) and document the residual TOCTOU window.
- **[medium/reliability/M] unzipToDirectory leaves partially-extracted files on limit/error** — `server/src/services/filesystem.ts:161-210`
  - issue: When a zip-bomb limit trips mid-extraction (too many files at line 170, per-file size at 194/200, total size at 204) the function throws but the already-written files/dirs remain on disk in destPath. There is no transactional extraction or cleanup, so a malicious or oversized archive both wastes disk and leaves a half-populated directory that the user must manually clean. The route (files.ts:191) returns the thrown error but no rollback occurs.
  - fix: Extract into a temp directory and atomically rename into place on success; on any error, rm -rf the temp dir. Alternatively track written paths and clean them up in a catch block.
- **[medium/quality/M] No path/input validation schema on file routes; missing/empty path yields 500s and inconsistent behavior** — `server/src/routes/files.ts:32-36,63-76,92-107,124-151,165-172`
  - issue: Routes declare TypeScript generics but register no Fastify JSON schema, so required fields aren't validated at the framework level. /files/read with no `path` passes undefined to safePath (returns workspaceRoot, then stat on a dir for readFileContent -> EISDIR 500). /files/search requires `query` but nothing rejects an empty/undefined query (an empty lowerQuery matches every entry, returning maxResults arbitrary files). parseInt(max) (line 170) is unguarded — `max=abc` yields NaN, making `results.length >= NaN` always false so the walk only stops at depth 10 (can return far more than intended or run long). newName in rename is not validated (could contain `/` to traverse, though safePath catches escapes, or be empty).
  - fix: Add Fastify schema objects (querystring/body) with required fields, types, and bounds (e.g. max as integer 1..500 with default). Validate query is non-empty in searchFiles and clamp maxResults. Reject newName containing path separators explicitly with a clear 400.
- **[medium/security/S] Content-Disposition filename header is unsanitized — header injection / broken downloads** — `server/src/routes/files.ts:69,74,215`
  - issue: Content-Disposition is built with `filename="${info.name}"` (and `${info.name}.zip`) using the raw basename. A filename containing a double-quote, CR/LF, or non-ASCII breaks the header or, with control characters, risks response-header injection. info.name comes from basename(absPath) of a user-created file, so an attacker who can create a file named e.g. `a";attachment;filename=evil` controls part of the header.
  - fix: Use RFC 5987 encoding: set `filename*=UTF-8''${encodeURIComponent(name)}` and a sanitized ASCII fallback for `filename=`, stripping quotes/CR/LF/control chars.
- **[medium/bug/S] upload destPath join is naive — missing separator and no safePath on the zip-extract dest before unzip writes** — `server/src/routes/files.ts:180-202`
  - issue: fullPath = `destPath.endsWith('/') ? destPath + data.filename : destPath` (line 181): if destPath does NOT end with '/', the uploaded file is written to destPath itself (treating it as the full target path), but the code never appends data.filename, so a client passing a directory like `/uploads` (no trailing slash) silently overwrites a file named `uploads` rather than creating `uploads/<filename>`. For the extract branch, unzipToDirectory(buffer, destPath) is called with the raw destPath; safePath is applied inside unzip, which is fine, but the non-extract branch's fullPath join can also place the file in an unexpected location. The dirname mkdir (line 199) then creates whatever parent results.
  - fix: Always treat destPath as a directory: fullPath = join(destPath, data.filename) (after stripping any trailing slash), and reject filenames containing separators. Validate data.filename is present (it can be undefined for some multipart payloads).
- **[low/ux/S] Lock check returns 200 with {success:false} instead of 409/423 status** — `server/src/routes/files.ts:100-101,114-115,232-233`
  - issue: When a file is locked or a lock acquisition conflicts, the endpoints return HTTP 200 with `{success:false, error:'...'}`. Clients that branch on HTTP status (or generic fetch error handling) will treat these as success. This is inconsistent with the global error handler which uses proper status codes, and makes lock conflicts easy to miss client-side.
  - fix: Return reply.status(423) (Locked) or 409 (Conflict) for lock conflicts so clients can reliably detect them, keeping the {success:false} body for compatibility.
- **[low/quality/M] Binary detection only samples first 8KB and whole file is loaded; large text/binary misclassification and full-file read** — `server/src/services/filesystem.ts:53-69`
  - issue: readFileContent reads the entire file (up to 50MB) into memory even when it will base64-encode it (further inflating memory ~1.33x). Binary detection only checks the first 8KB for NUL bytes, so a file that is text in its first 8KB but binary later is mis-served as UTF-8 (mojibake), and a UTF-16 text file with no NULs in the sample could also be mishandled. The 50MB cap still permits very large in-memory reads.
  - fix: Lower the read cap for the editor path (e.g. 5–10MB) and return a 'too large / open as download' signal; sample more bytes or use a content-type sniff; avoid base64-in-JSON for large binaries (use /serve streaming instead).

### Server: git (server/src/routes/git.ts, server/src/services/git.service.ts) (`server-git`) — 10 findings
> The git subsystem is a thin Fastify route layer over simple-git, with a sound security foundation: every route is gated by `fastify.authenticate` (git.ts:6), all repo/file paths flow through `safePath()` which blocks traversal, drive letters, UNC paths, NUL bytes, protected segments (.git/.env/.ssh) and symlink escape, and a `rejectOptionLike()` guard rejects user values beginning with "-" to defend against git argument-injection RCEs. simple-git is at 3.36.0 (current, post option-injection patches). The global error handler scrubs 5xx detail and maps PathTraversalError to 403. However the layer is weak on correctness and UX around git's real-world edge cases: there is zero input validation (no Fastify schemas, no required-field/type checks) so missing or malformed `repo`/`message`/`branch`/`files`/`max`/`depth` produce opaque 500s; merge conflicts, non-fast-forward push rejections, and missing-upstream all collapse into a generic "Internal server error" with no actionable signal; detached-HEAD state is silently dropped from every status/branch response; `gitDiscard` omits the option guard its siblings have; and `scanForRepos` has an unbounded-recursion bug when `depth` is non-numeric and no node count/time cap. Functional but brittle and low-fidelity for a real git UI.

- **[high/reliability/S] scanForRepos recurses unbounded when depth query param is non-numeric** — `server/src/routes/git.ts:116; server/src/services/git.service.ts:148-149`
  - issue: The route does `depth ? parseInt(depth) : 3` with no NaN/range check. `parseInt('abc')`, `parseInt('')`-style junk, etc. yield NaN. In scan(), the guard `if (depth > maxDepth) return;` is ALWAYS false when maxDepth is NaN (NaN comparisons are false), and `depth + 1` stays NaN, so the depth cap never trips. A request like `GET /git/scan-repos?path=/&depth=x` walks the ENTIRE workspace tree (every non-dot, non-skipped directory) regardless of intended depth, doing a readdir per directory. On a large workspace this is a denial-of-service / very slow response. A negative depth (`depth=-1`) instead returns nothing because `0 > -1` is true at the root.
  - fix: Parse defensively: `const d = parseInt(request.query.depth ?? '', 10); const depth = Number.isFinite(d) && d >= 0 ? Math.min(d, 10) : 3;`. In scan(), also guard against NaN explicitly and add an absolute node/time budget (e.g. stop after N directories scanned) so a deep tree can never hang a request.
- **[high/ux/M] Merge conflicts, non-fast-forward push, and missing upstream surface as generic 500 with no actionable detail** — `server/src/services/git.service.ts:56-73; server/src/app.ts:80-83`
  - issue: gitPull/gitPush let simple-git throw raw GitError on the common, expected failures: merge conflict, 'Updates were rejected because the tip of your current branch is behind' (non-fast-forward), 'There is no tracking information for the current branch' / 'no upstream', detached HEAD push, auth failure. The global error handler (app.ts:80) treats every thrown error as status 500 and replies with the opaque string 'Internal server error', logging the real reason server-side only. A git UI client therefore cannot tell a real server fault from a routine 'you have conflicts' or 'set an upstream first', and the user gets no path forward.
  - fix: Catch GitError in gitPull/gitPush (and gitCheckout) and translate known stderr patterns into typed errors with a 409/422 statusCode and a safe, specific message (e.g. 'Merge conflict in N files', 'Push rejected: remote has commits you do not have — pull first', 'No upstream configured for branch X'). Fastify will then pass the 4xx message through to the client. Optionally return conflicted file list from `git.status()` after a failed pull.
- **[medium/bug/S] Detached HEAD state is silently dropped from status/branch/current responses** — `server/src/services/git.service.ts:24-38 (gitStatus), 87-94 (gitBranches), 125-129 (gitCurrentBranch)`
  - issue: simple-git's StatusResult and BranchSummary both expose a `detached` boolean, and in detached HEAD `current` is null/'' (status) or the branch list omits a real branch. gitStatus maps only current/tracking/ahead/behind/files and never forwards `detached`; gitCurrentBranch returns `result.current` which is '' when detached; gitBranches returns current ''. The GitStatus type (utils/types.ts:51-57) has no `detached` field. A client showing 'current branch' will render blank/null and the user has no indication they are in detached HEAD (a state that loses commits on checkout). Checking out a commit hash via /git/checkout also enters this state with no warning.
  - fix: Add `detached: boolean` to GitStatus and the branch DTO; forward `status.detached` / `branchSummary.detached`. Have gitCurrentBranch return a sentinel like `(detached: <shorthash>)` or surface the detached flag so the UI can warn.
- **[medium/quality/M] No input validation on any git route — missing/malformed body or query yields opaque failures** — `server/src/routes/git.ts:9-119 (all handlers)`
  - issue: Unlike auth.ts (which attaches Fastify `schema:` to every route), no git route declares a body/querystring JSON schema or does manual presence/type checks. Examples: POST /git/commit with no `message` calls `git.commit(undefined)` → cryptic 500; POST /git/add / /git/discard with `files` not an array → `rejectOptionLike(...files)` throws TypeError on non-iterable or `files.join` (route line 101) throws; GET /git/status with no `repo` passes undefined to safePath (returns workspaceRoot — runs git on the whole workspace silently). Validation gaps degrade UX (500s instead of 400s) and make the rejectOptionLike guard's type assumptions implicit.
  - fix: Add Fastify schemas to each route requiring `repo` (string, minLength 1) and the relevant fields (`message` non-empty string, `files` array of strings, `branch` string). This yields proper 400s with safe messages, removes the silent 'undefined repo => whole workspace' behaviour, and guarantees rejectOptionLike receives strings.
- **[medium/security/S] gitDiscard omits the rejectOptionLike option-injection guard its siblings apply** — `server/src/services/git.service.ts:102-105`
  - issue: Every other file/branch-taking function (gitAdd:41, gitCommit:47, gitCheckout:97, gitDiff:108, gitDiffStaged:117) calls rejectOptionLike on its user values, but gitDiscard does not, despite building `git.checkout(['--', ...files])`. The `--` separator does neutralize leading-dash filenames here, so this is not currently exploitable, but it is an inconsistent gap in the defence-in-depth layer the codebase explicitly maintains (comment at git.service.ts:10-15). If the `--` is ever refactored away the guard would be silently absent.
  - fix: Add `rejectOptionLike(...files);` at the top of gitDiscard for consistency with all sibling functions, even though `--` currently mitigates. Also validate `files` is a non-empty array.
- **[medium/missing-feature/M] gitCheckout cannot create/track new branches and ambiguously handles remote branches** — `server/src/services/git.service.ts:96-100; server/src/routes/git.ts:27-34`
  - issue: gitCheckout does plain `git.checkout(branch)` only. There is no way to create a new branch (checkout -b) — a core operation for any git UI — nor to check out a remote-only branch with tracking. Checking out a name that exists only as `origin/feature` will, depending on git config, either create a tracking branch or fail; checking out a commit hash silently detaches HEAD (see detached-HEAD finding). The route exposes a single `branch` field with no `create` option.
  - fix: Add an optional `create: boolean` (→ `git.checkoutBranch`/`git.checkoutLocalBranch`) and/or a dedicated /git/branch (POST) create endpoint. Document that bare checkout of a hash detaches HEAD and surface that state back to the client.
- **[low/perf/S] gitLog max count is unbounded and unvalidated** — `server/src/routes/git.ts:80; server/src/services/git.service.ts:75-85`
  - issue: `max ? parseInt(max) : 20` is passed straight to `git.log({ maxCount })`. `parseInt('abc')` → NaN (simple-git then ignores maxCount and returns the FULL history — potentially tens of thousands of commits serialized into JSON), `parseInt('999999999')` is accepted, and negative values are passed through. On a large repo this is a heavy response with no cap.
  - fix: Clamp: `const n = parseInt(max ?? '', 10); const maxCount = Number.isFinite(n) && n > 0 ? Math.min(n, 500) : 20;`. Consider adding pagination (skip/`--skip`) for a real log view.
- **[low/reliability/S] /git/push and /git/checkout audit-log success but failures are not audited; push records no remote/branch** — `server/src/routes/git.ts:32,51,61,71,101`
  - issue: audit() is only called AFTER the service call resolves, so a rejected push/commit/checkout (the security-interesting cases — e.g. someone attempting to push to an unexpected remote) leaves no audit trail at all. Additionally git_push audits only `repo` (git.ts:61) — not the `remote`/`branch` actually pushed to — so the audit record cannot answer 'what was pushed where'. git_pull/checkout do capture detail, making this inconsistent.
  - fix: Record the attempted remote/branch in the push audit detail. Consider auditing failures too (wrap in try/finally or log a git_*_failed action in the error path) so denied/failed sensitive operations are visible in the audit log.
- **[low/security/S] rejectOptionLike only checks leading dash, not values that decompose to options after trimming or that are empty** — `server/src/services/git.service.ts:16-22`
  - issue: The guard checks `v.trimStart().startsWith('-')`. It does not reject an empty string or whitespace-only value (passed as a branch/remote these produce confusing git errors rather than a clean rejection), and it relies on the assumption that all values are strings — if a route passes a non-string (e.g. number/array element via unvalidated body, see the no-schema finding) the `typeof v === 'string'` check skips it silently, so a malformed payload bypasses the guard rather than being rejected. The guard is also applied per-call rather than centrally, so any new function can forget it (as gitDiscard did).
  - fix: Tighten to also reject empty/whitespace-only values where a non-empty token is required, and pair the guard with route-level schema validation guaranteeing string types so non-string bypass is impossible. Consider a single chokepoint that validates all task arguments.
- **[low/ux/S] gitStatus / gitBranches run against workspace root when repo is omitted instead of erroring** — `server/src/services/git.service.ts:5-8,24; server/src/utils/path-guard.ts:42-45`
  - issue: getGit(undefined) → safePath(undefined) returns config.workspaceRoot (path-guard.ts:43 treats falsy as root). So GET /git/status with no `repo` silently operates on the workspace root rather than rejecting. If the workspace root happens to be a git repo this returns its status; if not, simple-git throws 'not a git repository' → generic 500. Either outcome is surprising and masks a client bug (missing repo param).
  - fix: Require `repo` via schema (see validation finding), or explicitly reject empty repo in the service with a 400. At minimum, when checkIsRepo() is false return a typed 4xx 'not a git repository' rather than letting it become a 500.

### Server: terminal, claude, websocket handler (`server-term-claude`) — 12 findings
> The subsystem is reasonably mature on the security basics: WS connections require a single-use ticket plus Origin check, per-user terminal ownership is enforced on every terminal:* message (input/resize/destroy/attach), secrets (JWT_SECRET, AUTH_PASSWORD*, ANTHROPIC_API_KEY) are stripped from spawned env, the file-watcher refuses symlink-follow and filters sensitive basenames, and an orphan sweeper grace-kills detached PTYs after 60s. However, the Claude channel is the weak spot: it has none of the ownership, concurrency-cap, or input-validation rigor applied to terminals — any authenticated client can stop any other user's Claude session by guessing/observing a sessionId, there is no per-user cap on Claude subprocesses (the MAX_TERMINALS fork-bomb guard does not apply), and prompt/cwd are passed unvalidated. Several reliability gaps exist: cols/rows are never clamped or type-checked (NaN/huge/zero values flow straight into pty.spawn/resize), the persisted session tables have no userId column and are never reconciled at startup so stale active=1 rows accumulate forever, listTerminalIdsForUser is dead code, and the claude-cli session never writes to the child's stdin nor closes it. Memory leaks are mostly bounded (output buffer capped, debounce timers cleared) but the claude listener Map can leak when a CLI session ends because the per-client claudeListeners entry is only deleted on explicit stop, not on the session's own close event.

- **[high/security/M] Any authenticated user can stop another user's Claude session (missing ownership check)** — `server/src/ws/handler.ts:331-342 (also 296-330)`
  - issue: The claude 'stop' handler calls stopClaudeCliSession(sessionId) for any sessionId supplied by the client, with no verification that the session belongs to client.userId. Unlike terminals (which check terminal.userId !== client.userId in handleTerminal, destroy, and attach), Claude sessions carry no owner at all — startClaudeCliSession/streamClaudeApi never record a userId. SessionIds are UUIDs returned to the originating client but a malicious or buggy client that learns/guesses one (they are also written to a shared DB table) can kill another user's in-flight Claude run. There is likewise no path-scoping or ownership on the streamed output.
  - fix: Track the owning userId on each Claude CLI/API session (add a userId field to ClaudeCliSession and a userId column to claude_sessions). In the 'stop' handler, look up the session and reject with 'Access denied' if session.userId !== client.userId, mirroring handleTerminal. Only allow stop/attach/listen for sessions the requesting user owns.
- **[high/security/M] No per-user cap on Claude subprocesses — CLI fork-bomb / resource exhaustion** — `server/src/services/claude-cli.ts:30-83; server/src/ws/handler.ts:304-318`
  - issue: Terminals are hard-capped at MAX_TERMINALS_PER_USER (5) to prevent fork bombs, but the Claude channel has no equivalent limit. Each claude 'prompt' message spawns a new `claude --print` child process (or an API stream) with no per-user or global ceiling and no debouncing. A client (or a compromised token) can fire prompts in a tight loop and spawn unbounded subprocesses, exhausting CPU/memory/PIDs on the host. Each CLI process also holds a DB row and listener set.
  - fix: Add a per-user concurrency cap (e.g. countActiveSessionsForUser >= N → reject with a ClaudeLimitError) analogous to countTerminalsForUser, and consider a short per-user rate limit on 'prompt'. Reuse the userId now attributed to sessions for counting.
- **[medium/reliability/S] cols/rows are never clamped or validated before pty.spawn / pty.resize** — `server/src/ws/handler.ts:162-163,288-292; server/src/services/terminal.service.ts:60-83,162-169`
  - issue: On create, `const cols = data?.cols || 80` accepts any client value: a string ('abc' passes the `||` guard and reaches node-pty as a non-number), 0 (falls back to 80 via ||, but negative or huge values like 1e9 pass straight through), or floats. On resize, `if (data?.cols && data?.rows) resizeTerminal(data.cols, data.rows)` has no type/range check at all — a negative, zero, NaN-after-coercion, or absurdly large value is passed directly to ptyProcess.resize(), which can throw (crashing into the per-message catch but corrupting the PTY) or allocate huge terminal buffers. There is no Number.isInteger / clamp anywhere.
  - fix: Add a clamp helper, e.g. cols = Math.min(Math.max(Math.trunc(Number(data?.cols) || 80), 1), 1000) and the same for rows (cap ~e.g. 500), applied in both create and resize paths. Reject resize when values are not finite positive integers.
- **[medium/reliability/S] Persisted terminal/claude session rows are never reconciled at startup; stale active=1 rows leak forever** — `server/src/db/database.ts:58-72; server/src/services/terminal.service.ts:124-126,206-212; server/src/app.ts:122-124`
  - issue: INSERT writes active=1 and active is flipped to 0 on graceful exit (onExit, destroyAll on SIGINT/SIGTERM). But on a crash, SIGKILL, OOM, or power loss the shutdown handler never runs, so every terminal_sessions/claude_sessions row stays active=1 with a now-dead pid. On the next boot there is no `UPDATE ... SET active = 0` reconcile, so the table accumulates orphan 'active' rows indefinitely. Nothing ever reads these rows back to restore sessions either, so the persistence is effectively write-only bookkeeping that only grows.
  - fix: On startup, run `UPDATE terminal_sessions SET active = 0` and `UPDATE claude_sessions SET active = 0` (no in-memory session survives a restart, so all prior rows are by definition dead). Optionally add a periodic prune of old inactive rows to bound table growth.
- **[medium/perf/M] Claude CLI listener leaks from per-client map when session ends on its own** — `server/src/ws/handler.ts:311-318,331-342; server/src/services/claude-cli.ts:72-79`
  - issue: When a CLI prompt completes, proc 'close' fires, the service emits a 'done' event and calls activeSessions.delete(id). But the per-client entry client.claudeListeners.set(sessionId, listener) is only ever removed in the explicit 'stop' handler or on socket close. For a long-lived socket that issues many prompts that each finish normally, claudeListeners grows without bound (one stale entry per completed prompt), and on socket close the close handler then calls removeClaudeCliListener for sessions that no longer exist (harmless but indicates the leak). The API path (streamClaudeApi) never registers a client-side listener entry at all, so its sessions are inconsistent with the CLI path.
  - fix: Have the per-client listener delete its own claudeListeners entry on the 'done'/'error' terminal events, or register an onClose callback from the service that prunes the client map entry. Unify CLI and API session lifecycle so both register/unregister symmetrically.
- **[low/bug/S] API 'started' message can arrive after stream output due to async ordering** — `server/src/ws/handler.ts:319-325; server/src/services/claude-api.ts:28-67`
  - issue: streamClaudeApi is async and returns sessionId only after `const sessionId = await streamClaudeApi(...)`. The stream's onStream/onError callbacks fire as soon as the SDK starts producing events, which can be before the awaited promise resolves and the handler sends the 'started' message. A client relying on receiving 'started' (with the sessionId) before any 'stream' chunk can mis-order or drop the early chunks. The CLI path sends 'started' synchronously before output, so the two modes behave inconsistently.
  - fix: Generate the sessionId and send the 'started' message before attaching stream handlers (return the id synchronously, or pass it into the callbacks), so the client always learns the sessionId first. Keep CLI and API ordering identical.
- **[low/bug/S] Claude CLI child stdin is opened ('pipe') but never written or closed** — `server/src/services/claude-cli.ts:40-44`
  - issue: spawn is configured with stdio: ['pipe','pipe','pipe'] but the prompt is passed entirely via argv (`claude --print -- prompt`) and proc.stdin is never used or ended. Leaving stdin as an open pipe that is never closed can cause some CLIs to wait on stdin (depending on `claude --print` semantics) and leaves a dangling pipe fd for the lifetime of the process. There is also no stop/timeout if the CLI hangs.

- **[low/reliability/S] Claude prompt and cwd are not validated as strings before spawning** — `server/src/ws/handler.ts:304-312; server/src/services/claude-cli.ts:40`
  - issue: handleClaude destructures { prompt, cwd, mode } from arbitrary client data with no type checks. If prompt is undefined/an object/array, it is passed straight into spawn('claude', ['--print','--', prompt]) where node child_process requires args to be strings — a non-string throws a TypeError (caught per-message, but the session row may already be INSERTed in some paths) or, for an array, could inject extra argv-like behavior depending on coercion. cwd is run through safePath (good) but only after the value is trusted to exist. mode is unchecked.

  - issue: listTerminalIdsForUser is exported with a doc comment stating it is 'Used by the WS handler to know which terminals to grace-kill on disconnect,' but grep shows it is referenced nowhere. The socket 'close' handler only removes listeners (which lets the orphan sweeper eventually reap PTYs after 60s) — it never enumerates the user's terminals.   - issue: createTerminal sets orphanedAt = Date.now() so a terminal is 'orphaned' from birth and only becomes attached when addTerminalListener runs. - **[low/security/S] Empty userId collapses all anonymous terminals into one shared ownership bucket** — `server/src/services/terminal.service.ts:60-64,52-58; server/src/ws/handler.ts:151-294`
  - issue: createTerminal defaults userId to '' and the comment notes 'an empty userId means anonymous and shares one bucket.' In the WS path userId always comes from a validated ticket (auth.userId) so this is not currently exploitable, but any future caller that omits userId would create terminals owned by '' — which the ownership checks (terminal.userId !== client.userId) would then match for any other client whose userId is also '' . - **[low/perf/M] Claude listener output is not Origin/subscription-scoped and large outputs are unbounded in memory per send** — `server/src/ws/handler.ts:313-324; server/src/services/claude-cli.ts:58-70`
  - issue: Claude CLI stdout/stderr chunks are forwarded verbatim to the client with no aggregate cap (terminals cap scrollback at MAX_BUFFER_SIZE; Claude has no analogous backpressure or size accounting). A runaway model/tool output or a `claude` invocation that streams megabytes will be buffered and JSON.stringify'd per chunk and pushed onto the socket with no flow control, and there is no per-session output ceiling to terminate a misbehaving run.
  - fix: Add a per-session output byte budget that stops/ends the session when exceeded, and consider checking ws.bufferedAmount to apply backpressure when the client is slow. At minimum cap total streamed bytes per Claude session.

### Server: bootstrap, setup, config, db, locks (`server-infra`) — 12 findings
> The bootstrap/config/db/lock subsystem is generally well thought-out and security-conscious: config precedence (env > config.json > default) is explicit and correctly treats empty env strings as unset; JWT secret validation rejects known defaults plus low-entropy strings; config.json is written 0600; the CORS/WS origin allowlist is shared and uses an exact-match regex; setup mode degrades gracefully into a web wizard and requires an out-of-band token when bound beyond loopback; the DB uses WAL + foreign_keys, idempotent CREATE TABLE IF NOT EXISTS, and a real additive migration for users.token_version. However there are concrete reliability and consistency bugs. The most serious is that routes/projects.ts persists and locks an arbitrary client-supplied path with NO safePath() validation (unlike files.ts), so recent_projects and the locks table accept unbounded/escaping paths. There is a password-policy split-brain (CLI=8, web setup=12, web form client-side=8). The graceful-shutdown path never closes the SQLite DB and leaks all setInterval cleanup timers (not unref'd, never cleared). The handoff from setup-server to app.js can silently lose the chosen port (app reads it from config.json, but a stale PORT env can diverge), and the periodic cleanup interval in app.ts duplicates a second 60s timer already created inside LockService's constructor. getLocksForProject builds a LIKE pattern without escaping % / _ so project paths containing those characters over-match. None of these are crashes at rest, but several are correctness/data-integrity issues worth fixing.

- **[medium/reliability/S] Graceful shutdown never closes the SQLite database** — `/home/debian/projects/apps/projectx/server/src/app.ts:121-130; /home/debian/projects/apps/projectx/server/src/db/database.ts:19`
  - issue: The shutdown handler stops the file watcher, destroys terminals, and calls fastify.close(), but never calls db.close(). With WAL mode an unclean exit leaves a -wal/-shm sidecar and risks losing the last checkpoint; on a clean SIGTERM the DB should be closed so WAL is checkpointed and the handle released. There is also no try/catch — if fastify.close() rejects, process.exit(0) is never reached and the process can hang on SIGTERM (systemd/Docker would then SIGKILL it).
  - fix: In shutdown(), wrap the cleanup in try/finally, call db.close() (after fastify.close()), and always process.exit. Consider a watchdog timer (setTimeout(...).unref()) that force-exits after a few seconds if close() stalls.
- **[medium/quality/S] Password policy is inconsistent across the three setup entry points (8 vs 12 chars)** — `/home/debian/projects/apps/projectx/server/src/setup.ts:64; /home/debian/projects/apps/projectx/server/src/setup-server.ts:15,64,95`
  - issue: The interactive CLI wizard enforces MIN_PASSWORD_LENGTH=8 (setup.ts:64). A user who types an 8–11 char password in the web form passes client validation, POSTs, and gets rejected by the server with 'must be at least 12 characters' — a confusing UX, and the on-screen hint is simply wrong. The comment on setup-server.ts:15 even claims it is 'aligned with the configured server's policy' while setup.ts uses 8.
  - fix: Pick one policy (ideally 12) and apply it uniformly: update setup.ts MIN_PASSWORD_LENGTH, the web form label (line 64), and the client-side check (line 95) to match the server-side constant.   - issue: The setup server reads port from process.env.PORT||'3000' (setup-server.ts:115) and writes that same value into config.json (line 163). ### Desktop (Electron + React) (`desktop`) — 15 findings
> The desktop app is a well-structured Electron shell that bundles and supervises the ProjectX server (single-instance lock, stale-PID kill, health polling, tray, hide-to-tray) plus a React/Tailwind dashboard with seven pages, a first-run SetupWizard, an auth context, and an auto-updater banner. ### Flutter: UI/UX & IDE-dark theme adherence (`flutter-ui`) — 15 findings
> The IDE-dark design system in theme.dart is well-conceived: a coherent AppColors token set (canvas/surface/inset, semantic success/warning/danger, single blue accent), a thorough component theme (cards, inputs, buttons, chips, snackbars), and a clear typography intent (Inter for UI, JetBrains Mono for code/paths). ### Cross-cutting: end-to-end flows & API contracts (server ↔ desktop ↔ flutter) (`flows-e2e`) — 12 findings
> The three-tier contract is mostly coherent: REST envelopes are uniformly `{success, data|error}`, JWT+ws-ticket auth is well-designed (HS256 pin, token_version revocation, single-use 60s WS tickets, origin checks on the WS handshake), and the git/file/terminal/claude request shapes line up field-for-field with the Flutter models in the happy path. The security hardening noted in memory (path-guard, rate-limit keying, generic 5xx, secret-stripped pty/CLI env) is present and solid. The weaknesses are concentrated in error-contract handling and unfinished real-time wiring: several mutating file routes return application-level failures as HTTP 200 `{success:false}` that the Flutter client never inspects (silent data-loss on a locked save being the worst), the server's entire `files` watch channel is broadcast but consumed by no client (dead feature — no live refresh anywhere), API-mode Claude sessions can't be stopped, a stale token at the WS layer leaves the app permanently "Disconnected" with no re-login trigger, the two desktop QR generators disagree (Dashboard encodes a useless `localhost` URL), and the first-run setup password rule is stated three different ways (8 vs 12 chars) across the UI and server. None are exploitable, but they produce confusing, occasionally lossy behavior at the seams.

- **[high/bug/S] Locked-file save silently reported as success — data loss** — `server/src/routes/files.ts:99-107 (PUT /files/update) and flutter_app/lib/services/api_service.dart:36-38 + flutter_app/lib/providers/file_provider.dart:112-122`
  - issue: When a file is locked by another user, the server returns HTTP 200 with `{success:false, error:'File is locked by another user'}` (files.ts:100-101). The Flutter client `updateFile()` is `Future<void>` and never reads `response.data['success']`, so `saveFile()` treats the 200 as success, sets `hasUnsavedChanges = false` and shows the 'Saved' SnackBar (editor_screen.dart:162-166). The user's edits are discarded with a success confirmation. The same 200-`{success:false}` pattern with no client check applies to DELETE /files/delete (files.ts:114-115 vs api_service.dart:40-41).
  - fix: Either (a) make these routes return HTTP 409 on lock conflict so Dio throws and the provider's catch surfaces the error, or (b) have `updateFile`/`deleteFile` parse `response.data['success']` and throw when false. In `saveFile()` only clear `hasUnsavedChanges` after a confirmed success.
- **[medium/missing-feature/M] File-watch channel broadcast by server but consumed by no client — no live file refresh** — `server/src/ws/file-watcher.ts:66-73 and server/src/ws/handler.ts:239-260; no consumer in flutter_app/lib (grep for channel 'files' finds none) and no WS in desktop/src`
  - issue: The server runs a chokidar watcher that broadcasts `{channel:'files', type:'created|modified|deleted', data:{path}}` and implements a full subscribe/unsubscribe path-scoping protocol (handler.ts:241-258). No Flutter provider or service listens on the 'files' channel, and the desktop app uses no WebSocket at all. So when a terminal command, Claude, or another user changes files, the open editor and the file list never auto-update; the user sees stale content until a manual reload. The client also never sends `files/subscribe`, so the scoping feature is entirely dead.
  - fix: Wire a Flutter listener on `wsService.channelStream('files')` that invalidates/reloads the current directory in `FileProvider` and flags the open file as externally-changed in `EditorScreen`. Optionally send `files/subscribe` with the current path to use the existing server-side scoping.
- **[medium/bug/M] Claude API-mode sessions cannot be stopped (stop only wired for CLI)** — `server/src/ws/handler.ts:319-343 (handleClaude); server/src/services/claude-api.ts:28-68`

> The release pipeline is unusually thoughtful for a solo OSS project: a single tag-triggered workflow builds Windows/macOS desktop installers with conditional Apple signing/notarization, rebuilds native modules against Electron's ABI, builds the Android APK, and correctly flips the electron-builder draft release to published so electron-updater can see it. - **[high/reliability/M] Three independent version numbers can never align with the single v* release tag** — `server/package.json:3 (1.1.9), desktop/package.json:3 (1.1.12), flutter_app/pubspec.yaml:19 (1.0.3+4), .github/workflows/release.yml:4-6`

A tag (e.g. v1.1.12) only matches one component; electron-updater compares the running desktop version against the GitHub release tag, so a mismatch between the git tag and desktop/package.json `version` will either suppress a real update or offer a phantom one, and there is no CI guard that the tag equals desktop/package.json version.
